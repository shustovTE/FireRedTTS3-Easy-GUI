# Проверка металлического звучания длинных реплик

Для SGLang и сохранённого голоса `Dovbish_Anastasiia`:

```bash
cd /home/firered-tuning
git pull --ff-only origin feat/russian-tts-adaptation
bash scripts/diagnose_long_speech.sh
```

Контейнер по умолчанию — `sglang-fire-tts-firered-tts3-1`. Другие контейнер
и голос можно передать первым и вторым аргументами. Скрипт делает 12
последовательных запросов к уже работающему серверу; настройки сервера не меняет.
Задаёт Russian, seed=1234 и stop_threshold=0.5. Для другого seed/порога:

```bash
DIAG_SEED=1235 DIAG_STOP_THRESHOLD=0.5 bash scripts/diagnose_long_speech.sh
```

Каждый запуск сохраняет результаты в новую `training/eval/long-speech-XXXXXXXX`.
Сначала сравните:

- `long_stream.wav` и `long_full.wav`: первые три предложения одним запросом.
- `sentences-3_joined_stream.wav` и `sentences-3_joined_full.wav`: тот же текст,
  но каждое предложение синтезировано отдельным запросом с тем же голосом.
- `sentence-02_stream.wav`, `sentence-03_stream.wav`: проблемная середина
  отдельно. Есть соответствующие `*_full.wav`.
- `sentences-5_joined_*.wav`: все пять предложений по отдельности, соединённые
  для прослушивания. Файлы `*.boundaries.json` показывают границы запросов.

Поток сохраняется напрямую в PCM, затем упаковывается в WAV без пересэмплирования,
нормализации или добавленной тишины. Сохраняются JSON запросов, HTTP-заголовки,
статусы завершения, длительности и SHA256. `settings.json` содержит доступные
метаданные версии runtime и релиза модели. Наличие WAV не подтверждает
произнесение всего текста: проверяйте и звук, и `finish_reason`.

## Почему контроль содержит три предложения

В исходном примере 470 символов. В runtime
`a1e25be2cee83ad0425f623553da21a5c9e3efe8` preprocessing отклоняет input длиннее
400 символов. Сам по себе он не делит такой input на предложения. Первые три
предложения занимают 371 символ и содержат участок с сообщённым дефектом;
они помещаются в один запрос без изменения лимитов или обрыва слов.

400-й символ исходного текста находится около «Он поможет определиться с де…» —
рядом с сообщённым восстановлением звука. Это повод проверить фактические
`input` и границы запросов бота. Это не доказательство, что бот режет именно
на 400 символах: у него могут быть другие правила, а runtime мог измениться.

## Как интерпретировать

- Плохой длинный сохранённый поток при хорошем полном WAV: проверяем путь
  стриминга SGLang и декодер. Одинаковый seed не гарантирует идентичные латенты
  при разных режимах и нагрузке; одного сравнения мало для вывода о баге вокодера.
- Оба длинных WAV плохие, отдельные предложения хорошие: подтверждается
  зависимость от длины/контекста в этом тесте. Следующий контроль — native
  генерация с тем же референсом и адаптером, затем исходная база. По одному
  SGLang-тесту нельзя приписать причину датасету или LoRA.
- Оба прямых WAV хорошие, а бот звучит плохо: сопоставляем фактические input,
  модель, референс, настройки, нагрузку и обработку PCM в боте. Этот результат
  ещё не доказывает ошибку проигрывателя: запросы могли различаться.

В обучающей выборке YO были записи до 29.8 секунды до обрезки окончаний.
Длина записи сама по себе не означает плохой звук; MOS-фильтр также не гарантирует
отсутствие всех искажений. Пока причина не выделена, переобучение и удаление
длинных записей смешают несколько изменений и затруднят сравнение.

## Эксперимент: 2000 символов и весь пример одним запросом

`MAX_TEXT_CHARS = 400` — явная проверка длины `input` в
[preprocessing.py указанной версии SGLang](https://github.com/sgl-project/sglang-omni/blob/a1e25be2cee83ad0425f623553da21a5c9e3efe8/sglang_omni/models/firered_tts3/preprocessing.py#L65).
Она отклоняет слишком длинный input, а не автоматически разбивает его.
Это не установленный предел архитектуры или обучения FireRedTTS3. В этом коде
нет объяснения, почему выбрано именно число 400.

Следующий тест меняет только эту проверку. Потребуется перезапуск TTS-контейнера:
активные запросы при перезапуске будут прерваны.

```bash
cd /home/firered-tuning
git pull --ff-only origin feat/russian-tts-adaptation
bash scripts/set_sglang_text_limit.sh 2000
docker restart sglang-fire-tts-firered-tts3-1
DIAG_WHOLE_TEXT=1 bash scripts/diagnose_long_speech.sh
```

Диагностика ждёт `/health` до 30 минут, затем сохраняет `long_full.wav` и
`long_stream.wav` для **всего текста, 470 символов, одним запросом**. Теперь
сравнивать их нужно с `sentences-5_joined_*.wav`. Запросы по предложениям остаются
контролем; модель, голос, seed и stop_threshold не меняются относительно
обычного диагностического запуска. `settings.json` фиксирует длину и значение
константы в исходном файле; фактический приём длинного запроса подтверждается
ответом API после перезапуска, а не только значением на диске.

Патч действует в текущем контейнере после `docker restart`. При пересоздании
контейнера или повторном checkout исходников его нужно применить снова.
Для проверки это намеренно временное изменение. Возврат:

```bash
bash scripts/set_sglang_text_limit.sh 400
docker restart sglang-fire-tts-firered-tts3-1
```

2000 символов не означают, что модель гарантированно озвучит столько текста:
контекст и лимит аудиопатчей независимы. В этой конфигурации стандартные 400
патчей соответствуют примерно 64 секундам. Для воспроизведения примера из 470
символов лимит патчей не меняем; проверяем полное произнесение и `finish_reason`.
Если бот режет текст до отправки, увеличение серверного лимита его поведение
не изменит — прямой тест обходит это разбиение.

## Другой текст из файла, без перезапуска

Когда контейнер уже работает с лимитом 2000, пример «Михаил, я вас поняла…»:

```bash
cd /home/firered-tuning
git pull --ff-only origin feat/russian-tts-adaptation
DIAG_TEXT_FILE=examples/diagnostics/long-mikhail.txt \
  bash scripts/diagnose_long_speech.sh
```

Будут ровно два запроса: весь файл одним `input` со стримингом и без него.
Сохраняются внутренние переводы строк, пунктуация и написание слов; убираются
только внешние пробелы/переносы строк. В новой папке результатов появятся
`long_stream.wav`, `long_full.wav`, `original_text.txt`, JSON запросов и отчёты.
Голос, seed и stop_threshold остаются прежними. Автоматического разбиения
произвольного текста на предложения в этом режиме нет.
`DIAG_TEXT_FILE` принимает UTF-8 файл с текстом длиной 1–2000 символов;
относительный путь считается от корня репозитория.
