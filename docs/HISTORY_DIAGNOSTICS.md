# RedAE и влияние собственной истории генерации

Это две проверки **без обучения**, с генерацией целых реплик. Они нужны,
чтобы проверить гипотезу накопления ошибок до реализации нового режима обучения.

Эксперимент обучения по результатам этих проверок описан отдельно:
[Rollout-11: собственная акустическая история](ROLLOUT_FROM_BASE.md).

По умолчанию выбираются две самые длинные подходящие отложенные записи Common
Voice Spontaneous, предпочтительно разных дикторов, и одна самая длинная
отложенная Dialogs как короткий контроль. Для каждого target берётся другая
запись того же диктора и языка, предпочтительно около 6 секунд, максимум 30 с.
Совпадающее аудио, пересекающиеся размеченные отрывки и одинаковый текст пары
не допускаются. Manifest и аудио сверяются с fingerprint обучающего `joint-10`.

В существующей подготовке Common Voice target ограничен 30 секундами. Этот тест
покажет точные длительности выбранных записей; его успешный результат не означает
проверку 60-секундной речи. Порог выбора длинных target по умолчанию — 15 секунд.
Если подходящих пар меньше двух, запуск сообщает об этом вместо незаметного
перехода к коротким файлам. Дополнительный manifest для реальных более длинных
записей описан ниже. Синтетические WAV прошлых тестов не используются как эталон
реальной речи. Тексты «Города» и «Тимофей» здесь заменены транскриптами выбранных
реальных записей: для проверки teacher history нужна соответствующая аудиозапись.

## 1. Проверка кодека

Для каждой записи сохраняются три WAV:

- `source` — исходное аудио, приведённое к частоте RedAE;
- `codec` — RedAE encode → decode всей записи;
- `codec_with_reference` — тот же target latent, декодированный вместе с
  latent референса, как при TTS; звук референса удаляется из результата.

Последний вариант выявляет возможное влияние контекста декодера. Код учитывает,
что RedAE добавляет **левый padding**. При сопоставлении с оригиналом удаляется
ровно этот padding, сохраняется исходное число samples. Дополнительного
выравнивания громкости, поиска временного сдвига или обрезки окончаний нет.

Измеряются пики, RMS по секундным окнам, SNR и spectral convergence.
`reconstruction.active_window_gain_db` сравнивает уровень восстановления
с оригиналом в тех же временных окнах. Для почти тихих окон оригинала
ниже −50 dBFS отношение не вычисляется. `tail_gain_minus_head_gain_db` — разница
медианного усиления в последней и первой трети записи. Так естественное усиление
голоса в исходнике не выдаётся за дрейф кодека. Эти метрики не заменяют прослушивание.

## 2. Проверка истории

Сравниваются **исходная base и полный joint checkpoint 143**, seed 1234 и 1235.
Для каждой пары весов/seed выполняются три режима:

| Режим | История для backbone и DiT | Длительность |
|---|---|---|
| `teacher` | Предыдущие реальные target-патчи | Ровно число патчей реальной записи |
| `self_fixed` | Предыдущие собственные предсказания | То же число патчей |
| `free` | Предыдущие собственные предсказания | Штатный STOP 0.5 или максимум 400 патчей |

В `teacher` патч j предсказывается только по реальной истории **до j**.
Текущий и будущие target-патчи не подаются для предсказания j. Выход содержит
свежие ODE-предсказания, а не копию исходных латентов. Оба fixed-режима записывают
вероятности STOP, но игнорируют их при определении длины — иначе ранняя остановка
могла бы скрыть накопление искажений.

CFG 2, 10 ODE-шагов, исходный reference и последовательность начального шума
одинаковы. `free` вызывает штатный `core.generate`. Fixed-режимы используют его
же функции backbone/KV cache и `_flow_one_step`. В GPU-прогоне проверяется
совпадение общего префикса `self_fixed` с `free` и первого патча `teacher`
с `self_fixed`. При существенном расхождении сравнение останавливается.
Допуск: максимальная абсолютная ошибка <=2e-5 или относительная L2 <=0.02;
точные отклонения доступны в `controls`.

Предсказанные латенты всей реплики вместе с референсом проходят через RedAE
**одним вызовом**. Аудио не собирается из отдельно декодированных патчей и
не делится на предложения. Для fixed-режимов убирается известный левый padding
target, для `free` удаляется только reference, как в штатном генераторе.

`teacher` — диагностическое вмешательство: оно удерживает историю на реальной
траектории. Его WER не является оценкой самостоятельного TTS. Кроме того,
последовательность предсказаний, каждое из которых опирается на реальную историю,
может быть менее согласованной, чем свободная траектория. Поэтому даже плохой
`teacher` не исключает вклад накопления ошибок.

## Запуск на Gauss

```bash
cd /opt/firered-tuning
git pull --ff-only origin feat/russian-tts-adaptation

OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 \
  .venv/bin/python -m fireredtts3_local.history_diagnostics start
```

Нужны исходная base, checkpoint 143, существующие данные joint-10 и
`training/datasets/russian-joint-10/recipe.json`. Предрасчёт кэша не нужен:
эти несколько записей кодируются заново в нативном режиме. Код работает в фоне;
SSH можно отключить. Веса не обновляются. SGLang не затрагивается.

Всего по умолчанию **45 WAV**: 9 для исходников/кодека и 36 для сравнения истории.
Модели загружаются на GPU последовательно. После генерации отдельный процесс
проверяет все WAV через Whisper large-v3 на CPU int8, включая исходную запись
для контроля ошибок самого распознавателя. Кэш ASR используется повторно;
при его отсутствии загрузятся веса. Этот этап может занять больше времени,
чем GPU-генерация.

```bash
.venv/bin/python -m fireredtts3_local.history_diagnostics status

tail -n 30 -f training/jobs/joint-10-history/job.log
```

`Ctrl+C` закрывает просмотр. После `[job] Completed successfully.`:

```bash
.venv/bin/python -m fireredtts3_local.history_diagnostics summary

ls -lh training/eval/joint-10-history-diagnostics/diagnostics-*.zip
```

Пришлите `diagnostics-report.zip` и все `diagnostics-audio-*.zip` из этого каталога.
Они содержат отчёты и PCM WAV, в том числе выбранные реальные target-записи.
Reference WAV, его текст, plan, модель и исходные float WAV остаются локально.

Для честного прослушивания применяется **один постоянный gain ко всем вариантам
одного case**, только если общий максимальный пик требует запаса до 0.98.
Следовательно, различия громкости между весами и режимами внутри case сохраняются.
Метрики вычисляются до этого gain. Если один режим получился очень громким,
все варианты case могут звучать тихо; это видно в `pcm_gain`.

ASR получает исходный float waveform, переведённый в 16 kHz, с отдельным
постоянным уменьшением пика до 0.98 только при необходимости. Поэтому один
аномально громкий вариант не снижает точность остальных ASR-входов через
слишком тихую PCM16-копию. Значение записано в `asr.input_gain`; измерения
громкости и копии для прослушивания от этого не меняются.

## Как читать результат

`report.json` — все генерации, codec metrics, STOP, уровни латентов по патчам,
входные длины и проверки совпадения со штатным генератором.
`asr_report.json` — те же результаты с распознанным текстом, WER, пропусками,
заменами и временными метками. `summary.md/csv` — краткая таблица.

Общий RMS-дрейф сравнивает непересекающиеся начало/конец длительностью
`min(10 с, треть WAV)`; короткий контроль поэтому не получает искусственный ноль.
Его определение отличается от старого отчёта с фиксированными первыми/последними
10 секундами. Для codec важнее изменение усиления **относительно оригинала**.
Для свободной речи временного выравнивания с оригиналом нет: другие паузы,
темп и пропуски тоже влияют на RMS. Латентный RMS не равен громкости waveform.

- Если искажается `codec`, исследуем путь кодирования/декодирования и источник.
  Это ещё не отделяет encoder от decoder.
- Если ухудшается только `codec_with_reference`, проверяем влияние контекста
  декодирования и границы reference/target.
- Если кодек стабилен, `teacher` заметно лучше `self_fixed`, а `free` также
  деградирует, гипотеза накопления ошибок на собственной истории получает
  поддержку. Это всё ещё не гарантия успеха rollout-aware обучения.
- Если `self_fixed` стабилен, а `free` плохо завершает речь, отдельно разбираем
  STOP, пропуски текста и фактическую длину генерации.
- Сравнение base с checkpoint 143 показывает, как совместное дообучение изменило
  картину на этих записях. Автоматического выбора «лучшего метода обучения» нет.

Нужны и метрики, и прослушивание. Если дефект на этих реальных записях не
воспроизведётся, это не докажет его устранение на других голосах и длинных текстах.

## Остановка и продолжение

```bash
.venv/bin/python -m fireredtts3_local.history_diagnostics stop

OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 \
  .venv/bin/python -m fireredtts3_local.history_diagnostics start \
  --resume --job-dir training/jobs/joint-10-history-retry
```

Остановка сохраняет текущую тройку history-режимов либо текущую ASR-проверку.
Готовые группы используются повторно, незавершённая группа рассчитывается снова.
Возобновляйте после остановки с новым job-dir, теми же параметрами, кодом и
библиотеками. Нужен уже созданный `report.json`; если output не появился,
повторите с новым job-dir без `--resume`. Для status/stop возобновлённого задания
укажите его путь. Проверки хэшей не позволяют смешать изменённые данные или ASR.

## Дополнительные реальные длинные записи

`--long-manifest /path/to/manifest.jsonl` заменяет выбор длинных target, сохраняя
короткий Dialogs-контроль. Формат — обычный manifest репозитория: `audio`, `text`,
`speaker_id`, `language`, желательно `utt_id` и `source_id`. Нужны точные
подтверждённые транскрипты и отдельные reference-записи тех же дикторов длиной
2–30 секунд в этом же manifest. Автоматически подтвердить разметку пользовательского
manifest программа не может. Принимаются целые target до 90 секунд, без обрезки;
пересечение с обучающими аудио/источниками запрещено. Для `free` сохраняется
штатный предел 64 секунды, который нужно учитывать на более длинных target.

Для такого сравнения задайте новые `--output`, `--job-dir` и, например,
`--min-long-seconds 40`. Остальные параметры: `--step`, `--seeds`, `--long-count`,
`--data-recipe`, `--asr-model`; все сохраняются в плане. Не меняйте их при resume.
