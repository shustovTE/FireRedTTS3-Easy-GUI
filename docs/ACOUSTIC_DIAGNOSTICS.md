# Раздельная проверка DiT / dit_head и соответствия обучающего forward

Предыдущая диагностика checkpoint 143 локализовала регрессию в группе
`DiT + dit_head`: с исходным backbone обновление этой группы увеличило рост RMS
обеих контрольных реплик. С обновлённым backbone «Города» дошли до лимита 64 с.
Переключение stop_head в четырёх парах не изменило PCM ни одного из двух WAV.
Это результат для двух текстов, одного голоса, seed 1235 и CFG 2; он ещё не
разделяет вклад DiT и его conditioning-проекции.

Новый режим выполняет **18 нативных генераций**, без обучения:

- восемь сочетаний исходных/обученных **backbone LoRA, DiT и dit_head**, с исходным
  stop_head во всех восьми;
- полный checkpoint, включая обученный stop_head, как дополнительный контроль;
- по две прежние реплики: `cities_seed1235` и `timofey_seed1235`.

Исходная base входит в восемь сочетаний. CFG **2**, STOP **0.5**, 10 шагов flow,
разделение текста выключено. Reference, текст, язык и seed берутся из прежнего
benchmark. `projection` в именах вариантов означает только `dit_head`, а не
проекции голоса. RedAE и остальные замороженные модули остаются исходными.

## Запуск

```bash
cd /home/firered-tuning
git pull --ff-only origin feat/russian-tts-adaptation

OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 \
  .venv/bin/python -m fireredtts3_local.component_diagnostics start \
  --split-acoustic
```

Нужны исходные веса base, checkpoint 143, benchmark и его reference WAV.
Никакой новый предрасчёт или подготовка датасетов не требуется. Работа идёт
в фоне, SSH можно отключить. На GPU одновременно загружается один вариант.
Диагностика не меняет веса или работающий SGLang.

Для нового режима задавайте путь в командах просмотра состояния:

```bash
.venv/bin/python -m fireredtts3_local.component_diagnostics status \
  training/jobs/joint-10-acoustic

tail -n 30 -f training/jobs/joint-10-acoustic/job.log
```

`Ctrl+C` закрывает просмотр лога. Строка `[training-parity] ... passed=...`
показывает результат сверки forward после очередной генерации. `false` записывается
в отчёт; остальные варианты продолжают проверяться.

## Что проверяет training_parity

Во время обычной нативной генерации сохраняются входные tokens, speaker embedding,
prompt/target latents и ограниченный набор внутренних тензоров. После генерации
та же история проходит через **настоящие функции нашего пакетного обучения**
в eval-режиме, без градиентов и обновлений весов.

Для первых и последних четырёх сгенерированных патчей сравниваются:

- история скрытых состояний backbone и результат dit_head;
- входы DiT для conditional и unconditional ветвей;
- акустическая история и исходный шум — на точное совпадение;
- flow-предсказания обеих ветвей и их CFG-комбинация.

Дополнительно сравниваются stop logits на всех наблюдённых позициях, включая
терминальную, если генератор остановился по stop. В отчёт попадают только числовые
расхождения, а не reference latents или speaker embedding.

В GPU-прогоне эта сверка относится к **первому ODE-шагу, t=0**. На этом шаге
можно подать абсолютно тот же шум и историю без изменения нативной генерации.
На последующих ODE-шагах траектория генератора обычно не совпадает с линейной
интерполяцией, используемой для flow matching; их нельзя объявлять эквивалентными
входами без дополнительного построения.

Нативный backbone работает пошагово с KV cache, обучающий — одним проходом.
При BF16 результаты разных ядер могут немного различаться. Для каждого
сравниваемого патча проходят значения с максимальным абсолютным отклонением
не более `2e-5` **либо** относительной L2-ошибкой не более `0.02`. Для акустической
истории и шума требуется точное совпадение. Это диагностические допуски;
полные значения ошибок записаны в `training_parity.checks`.

Прохождение этой проверки не подтверждает оптимальность loss, градиентов,
датасета или устойчивость на собственных предсказаниях. Проверяется конкретное
соответствие входов и forward при одинаковой истории. Падение проверки также
нужно разобрать по отдельным полям: оно само по себе не доказывает ошибку формулы.

На CPU дополнительно проверены короткие/длинные prompts, батч с разными длинами
и padding, реальные PEFT-обновления и один нативный ODE-шаг при `t=0, 0.17, 0.8`.
Искусственный сдвиг истории обнаруживается. WAV, RNG и веса не меняются от
диагностического наблюдения. Производственные веса проверяются этим запуском
на Gauss; здесь они недоступны.

## Результат

```bash
.venv/bin/python -m fireredtts3_local.component_diagnostics summary \
  training/eval/joint-10-acoustic-diagnostics

ls -lh training/eval/joint-10-acoustic-diagnostics/diagnostics-*.zip
```

Передайте **`diagnostics-report.zip`** и все **`diagnostics-audio-*.zip`**.
В каталоге находятся `report.json`, `summary.md`, `summary.csv`, `plan.json`,
PCM WAV и исходные float WAV. Архивы не включают reference audio, его транскрипт,
speaker embedding или веса.

Имена вариантов: `base`, `all`, `backbone_dit_projection`, `backbone_only`,
`dit_only`, `projection_only`, `backbone_dit`, `backbone_projection`,
`dit_projection`. `case-00` — «Города», `case-01` — «Тимофей».

Сначала проверяем `reproduction_controls_complete` и
`reproduction_review_required` для base/all, затем `parity_review_required`
и расхождения отдельных forward-проверок. После этого сравниваем отдельные
модули и их сочетания. `all` и `backbone_dit_projection` различаются только
stop_head; прошлый тест не обнаружил разницы WAV, но это снова проверяем,
а не принимаем за универсальное свойство.

Ни отсутствие флагов, ни меньшая длительность не подтверждают полноту текста.
ASR/WER этот режим не считает. Группы обучались совместно, поэтому их смешивание
с base не равно независимому обучению каждой группы.

Для проверки полноты речи есть следующий [тест целого текста и отдельных
предложений с ASR](SENTENCE_DIAGNOSTICS.md): base, backbone-only и DiT-only,
те же два текста, 12 итоговых WAV. Он помогает отличить короткую корректную
генерацию от генерации, пропустившей часть текста.

## Остановка и продолжение

```bash
.venv/bin/python -m fireredtts3_local.component_diagnostics stop \
  training/jobs/joint-10-acoustic
```

Остановится после текущего случая. Для продолжения при наличии `report.json`:

```bash
OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 \
  .venv/bin/python -m fireredtts3_local.component_diagnostics start \
  --split-acoustic --resume \
  --job-dir training/jobs/joint-10-acoustic-retry
```

Готовые WAV повторно не генерируются. Входы, код и библиотеки должны совпадать
с сохранённым планом. Если output ещё не появился, повторите запуск с новым
`--job-dir` без `--resume`. Результаты предыдущих диагностик сохраняются
в своих отдельных каталогах.
