# Диагностика регрессии joint-10: CFG и ранние checkpoint

Для следующего этапа — разделения влияния backbone LoRA, DiT/dit_head и stop_head
при фиксированном CFG — есть [матрица компонентов checkpoint 143](COMPONENT_DIAGNOSTICS.md).

Эта команда выполняет **только нативную генерацию**, без обучения, слияния,
публикации или изменения работающего SGLang. Она использует существующие
checkpoint и benchmark прогона `russian-joint-base-10`.

Матрица по умолчанию — **24 WAV**:

| Параметр | Значения |
|---|---|
| Веса | Исходная base, шаги 50, 143, 286 |
| CFG | 0, 1, 2 |
| Случаи | `cities_seed1235`, `timofey_seed1235` |
| STOP | 0.5, одинаковый во всех случаях |
| Flow steps | 10 |
| Разделение текста | Выключено, как в контрольной генерации обучения |

В этом генераторе `CFG=0` использует только условную ветвь; `CFG=1` даёт
`2 × conditional − unconditional`; `CFG=2` — `3 × conditional − 2 × unconditional`.
Нулевой CFG не означает отключение текста или голоса.

Reference WAV, его транскрипт, целевой текст, язык и seed берутся из **того же**
benchmark, который записан в рецепте обучения. Другой голос или seed автоматически
не подставляются. Шаг 50 берётся из `adapter-step-000050`, шаги 143/286 — из
`checkpoint-step-000143` / `checkpoint-step-000286`. Если нужных файлов нет,
команда остановится с объяснением; `best-validation` вместо них не используется.

## Запуск на Gauss

Нужны исходная base в `models/FireRedTTS3`, сохранённый прогон и доступные
reference WAV. Нового предрасчёта и загрузки датасетов не требуется.

```bash
cd /home/firered-tuning
git pull --ff-only origin feat/russian-tts-adaptation

OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 \
  .venv/bin/python -m fireredtts3_local.cfg_diagnostics start
```

Запуск проверяет метаданные и хэши адаптеров, затем возвращает PID и пути.
Worker проверяет fingerprint исходной base и последовательно загружает четыре
варианта весов. Проверка файлов и загрузки занимают время до первой генерации.
На GPU одновременно находится один вариант. SSH можно отключить.

Диагностика использует блокировку исходного training output: через штатный
launcher нельзя одновременно продолжить этот же прогон и переписать его
checkpoint. Другие программы на GPU этот механизм не останавливает.

```bash
.venv/bin/python -m fireredtts3_local.cfg_diagnostics status

tail -n 30 -f training/jobs/joint-10-cfg/job.log
```

`Ctrl+C` закрывает просмотр лога. Для остановки самой диагностики после текущего
случая:

```bash
.venv/bin/python -m fireredtts3_local.cfg_diagnostics stop
```

Результат каждого случая сохраняется сразу. Итоговый `completed` — техническое
завершение матрицы, а не заключение, что качество речи хорошее.

## Посмотреть и передать результат

```bash
.venv/bin/python -m fireredtts3_local.cfg_diagnostics summary

ls -lh training/eval/joint-10-cfg-diagnostics/diagnostics-*.zip
```

Каталог `training/eval/joint-10-cfg-diagnostics` содержит:

- `summary.md` и `summary.csv` — компактную таблицу всех случаев;
- `report.json` — метрики, stop scores, акустические latents по патчам,
  нормы условного/безусловного/итогового flow-предсказания;
- `plan.json` — локальную привязку к checkpoint, reference, benchmark, настройкам,
  версиям библиотек и исходникам runtime;
- `base/cfg-0/case-00.wav`, `step-000050/cfg-2/case-01.wav` и аналогичные файлы;
- соответствующие `.float.wav` с исходными амплитудами.

По умолчанию `case-00` — `cities_seed1235`, `case-01` — `timofey_seed1235`.
Точное соответствие файлов и текстов записано в отчёте.

Для передачи результатов удобны:

- **`diagnostics-report.zip`** — сводка и полный отчёт без WAV;
- **`diagnostics-audio-01.zip`**, при необходимости `-02.zip` и далее — WAV для
  прослушивания, разбитые на части с исходным объёмом не более 24 МиБ.

Оригинальная запись голоса, её транскрипт, веса и локальный plan в архивы не
включаются. Float-WAV остаются на хосте; PCM-копии содержат всю генерацию без
обрезки. Если исходная амплитуда превышает ±1, PCM-копия ослабляется одним
постоянным коэффициентом, записанным как `pcm_gain`. Поэтому абсолютную громкость
между вариантами сравнивайте по float-метрикам, а не по одной лишь PCM-копии.

## Как читать сравнение

Каждый обученный вариант сравнивается с **base при том же CFG, тексте и seed**.
`rms_drift_delta_vs_base_same_cfg` показывает изменение нарастания RMS между
первыми и последними 10 секундами; это не LUFS и не оценка тембра. В коротких
файлах окна могут перекрываться. `latent_rms_ratio` относится к первым и последним
примерно 10 секундам сгенерированных latents; исходный prompt исключён.

`flow_by_patch` содержит средние по 10 шагам интеграции нормы conditional,
unconditional, их разности и итоговой CFG-комбинации. При CFG 0 безусловная ветвь
не вычисляется; её значения `null`, а не нули. Наблюдение не меняет веса, RNG
или значения предсказаний. Оно добавляет вычислительные расходы, поэтому время
этого запуска не следует считать чистым benchmark производительности.

Для CFG 2 поле `previous_monitor` сопоставляет результат с контрольной
генерацией того же шага при обучении. `reproduction_review_required` отмечает
различие причины завершения, длительности более чем на 0,161 с либо показателя
роста RMS более чем на 0,25 dB. Это инженерный сигнал для проверки
воспроизводимости, а не доказательство ошибки. У шага 50 прежнего отчёта обычно
нет, поэтому поле там `null`.

Сначала проверьте воспроизводимость CFG 2. Затем оцените, насколько изменение
CFG влияет на base и на адаптированные веса. Сравнение раннего шага 50 с 143/286
покажет, насколько рано появляется регрессия. Если меньший CFG улучшает результат,
это показывает чувствительность к guidance, но не доказывает единственную
причину артефактов или правильность обучения.

**Отсутствие флагов, меньшая длительность или меньший RMS не гарантируют, что
произнесены все слова.** Этот запуск не считает ASR/WER или сходство голоса.
Для выбора настроек нужны прослушивание полного текста и последующая проверка
других фраз/голосов. Обучение и публикация автоматически не запускаются.

## Продолжить после прерывания

После остановки или сбоя с уже созданным `report.json`:

```bash
OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 \
  .venv/bin/python -m fireredtts3_local.cfg_diagnostics start \
  --resume --job-dir training/jobs/joint-10-cfg-retry
```

Директория job должна быть новой. Готовые случаи не генерируются повторно;
проверяются хэши их WAV. Настройки, исходные checkpoint, reference, код генерации
и версии библиотек должны совпадать с сохранённым планом. Если сбой произошёл
до создания output, используйте новый job без `--resume`.

Для отдельного эксперимента задайте новые `--output` и `--job-dir`. При наличии
других сохранённых весов и benchmark cases можно менять `--steps`, `--cfgs`
и `--cases`. Исходная base автоматически остаётся первым вариантом сравнения.

Проверено на CPU с настоящим уменьшенным upstream AR/DiT-графом и PEFT:
наблюдение не меняет сэмплы; resume совпадает с непрерывной генерацией;
checkpoint/benchmark привязаны по хэшам; ошибки фонового процесса отражаются в
статусе. Производственные веса и GPU Gauss в среде разработки недоступны.
