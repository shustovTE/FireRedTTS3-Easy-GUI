# Диагностика joint-10 по компонентам checkpoint 143

Тест помогает выяснить, с какими обновлёнными компонентами появляется регрессия
длинной речи. Он использует исходную base и **существующий checkpoint 143**.
Все варианты генерируются нативным FireRedTTS3, без нового обучения.

| Вариант | Backbone LoRA | DiT + dit_head | stop_head |
|---|---|---|---|
| `base` | Исходные веса | Исходные веса | Исходные веса |
| `all` | Обученный | Обученные | Обученный |
| `backbone_only` | Обученный | Исходные веса | Исходные веса |
| `acoustic_only` | Исходные веса | Обученные | Исходные веса |
| `stop_only` | Исходные веса | Исходные веса | Обученный |
| `backbone_acoustic` | Обученный | Обученные | Исходные веса |
| `backbone_stop` | Обученный | Исходные веса | Обученный |
| `acoustic_stop` | Исходные веса | Обученные | Обученный |

Это **16 генераций**: восемь вариантов × `cities_seed1235` и `timofey_seed1235`.
CFG = **2**, STOP = **0.5**, 10 шагов flow; разделение текста выключено.
Тексты, голос, reference transcript, язык и seed берутся из прежнего benchmark
прогона. RedAE, PatchEncoder и извлечение/проекции голоса используют исходные веса.

`acoustic` здесь означает DiT и проекцию его conditioning `dit_head`, а не
волновой декодер RedAE. Эти два модуля проверяются одной группой.
При отключении компонента PEFT направляет вычисление через исходные веса base.
Параметры не обнуляются, не сливаются и не перезаписываются; каждый вариант
загружается заново, чтобы состояние предыдущего не влияло на следующий.

## Запуск на Gauss

Нужны исходная base в `models/FireRedTTS3`, сохранённый
`training/outputs/russian-joint-base-10`, его benchmark и reference WAV.
Предрасчёт признаков и датасеты для этого теста не нужны.

```bash
cd /home/firered-tuning
git pull --ff-only origin feat/russian-tts-adaptation

OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 \
  .venv/bin/python -m fireredtts3_local.component_diagnostics start
```

Команда возвращает PID и пути. Работа продолжается при отключении SSH.
Сначала проверяются файлы и fingerprint base; затем последовательно загружаются
восемь вариантов. На GPU одновременно находится один вариант. SGLang остаётся
отдельным процессом; диагностика его не останавливает и не перенастраивает.

```bash
.venv/bin/python -m fireredtts3_local.component_diagnostics status

tail -n 30 -f training/jobs/joint-10-components/job.log
```

`Ctrl+C` завершает просмотр лога. Чтобы остановить саму диагностику после
текущего случая:

```bash
.venv/bin/python -m fireredtts3_local.component_diagnostics stop
```

Исходный training output блокируется штатным механизмом фоновых заданий:
одновременно продолжить этот же прогон через launcher нельзя. Веса, старые
отчёты и результаты предыдущей CFG-диагностики остаются на месте.

## Результаты

```bash
.venv/bin/python -m fireredtts3_local.component_diagnostics summary

ls -lh training/eval/joint-10-component-diagnostics/diagnostics-*.zip
```

Передайте `diagnostics-report.zip` и `diagnostics-audio-01.zip` (если есть
следующие части, то и их). Отчёт содержит метрики всех вариантов, stop scores,
уровни latents и flow по патчам, выбранные компоненты и проверку их переключения.
Архивы WAV разбиваются на части объёмом до 24 МиБ до сжатия.

По умолчанию `case-00.wav` — `cities_seed1235`, `case-01.wav` —
`timofey_seed1235`. Например:

```text
training/eval/joint-10-component-diagnostics/base/cfg-2/case-00.wav
training/eval/joint-10-component-diagnostics/all/cfg-2/case-00.wav
training/eval/joint-10-component-diagnostics/acoustic_only/cfg-2/case-00.wav
```

Рядом сохраняются исходные `.float.wav`. PCM-копия ослабляется постоянным
коэффициентом только при необходимости избежать клиппинга; коэффициент указан
в `pcm_gain`. Поэтому абсолютный уровень сравнивайте по float-метрикам.
Reference WAV, его транскрипт, веса и локальный plan в архивы не включаются.

## Как интерпретировать

Сначала смотрим **base и all**. Для них обязательны предыдущие generation reports
шагов 0 и 143. В `report.json` должны быть
`reproduction_controls_complete: true` и `reproduction_review_required: false`.
Последний флаг проверяет причину завершения, отклонение длительности более чем
на 0,161 с и показателя роста RMS более чем на 0,25 dB. Это проверка метрик,
а не доказательство идентичности WAV. При расхождении сначала разбираемся
с воспроизводимостью.

У частичных вариантов `previous_monitor: null`: они намеренно отличаются от
полного checkpoint. Сравниваем, возникает ли тот же дефект при включении
каждого компонента отдельно и в сочетаниях. Если дефект появляется только
в сочетании, это указывает на взаимодействие компонентов.

Все три группы **обучались вместе**. Их смешивание с base не равно отдельному
обучению каждой группы. Даже если один вариант звучит лучше, это ещё не
доказывает единственную причину проблемы и не выбирает новый режим обучения.
Проверка двух фраз одним голосом также не подтверждает качество на других
голосах и текстах.

Автоматические флаги отмечают достижение лимита генерации, выход амплитуды за ±1
и усиление роста RMS относительно base. Меньшая длительность или отсутствие
флагов не гарантирует, что произнесены все слова. ASR/WER здесь не запускается;
для вывода нужно сопоставить WAV с текстами. Описания метрик есть в
[руководстве CFG-диагностики](CFG_DIAGNOSTICS.md).

## Продолжение после прерывания

Если output уже содержит `report.json`:

```bash
OMP_NUM_THREADS=4 MKL_NUM_THREADS=4 \
  .venv/bin/python -m fireredtts3_local.component_diagnostics start \
  --resume --job-dir training/jobs/joint-10-components-retry
```

Job directory должна быть новой. Готовые WAV проверяются по хэшам и повторно
не генерируются. Если ошибка произошла до создания output, запускайте с новым
`--job-dir` без `--resume`. При изменении кода, библиотек или входных данных
нужен новый `--output`: результаты разных условий не смешиваются.

Можно задать другой `--step` при наличии сохранённых весов и соответствующего
контрольного generation report, а также `--cases`. CFG и STOP в этой матрице
зафиксированы, чтобы сравнивать именно компоненты.

Проверено на CPU с уменьшенным настоящим upstream AR/DiT-графом и PEFT:
каждое сочетание соответствует явно собранным исходным/обученным весам,
переключение обратимо, исходные файлы сохраняются, результаты после resume
совпадают с непрерывным запуском. Производственная GPU-генерация выполняется
на Gauss; в среде разработки нет этих весов и GPU.
